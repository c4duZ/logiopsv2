  <action>
    For the confirmed primary feature ID, write into 08-SPIKE.md the full function map in the
    SAME shape SmartShift uses, so Plan 02 can transcribe it directly:

    1. A `enum Function { … }` table: for each function the UI needs — at minimum get-info/
       capabilities, get-current-state, set-brightness (and for RGB: set-effect / set-color) —
       give the function index, a name, the request param bytes (offset -> meaning -> range), and
       the response byte layout (offset -> meaning). Mirror the precision of BatteryStatus's
       wire-format comment block.
    2. Any broadcast/event function index (like BatteryStatus::BatteryStatusBroadcast) if the
       feature pushes state changes, OR state explicitly that there is no event and reads are
       on-demand.
    3. The CAPABILITY-DETECTION rule: the high-level DeviceFeature ctor calls
       `std::make_shared<hidpp20::Backlight>(&dev->hidpp20())`; if the device lacks the feature,
       the wrapper's Feature ctor throws hidpp20::UnsupportedFeature, which the high-level feature
       catches and rethrows as features::UnsupportedFeature so _addFeature swallows it (mirror
       DeviceBattery.cpp lines 26-41). Document that this is how "controls hidden on unsupported
       devices" (success criterion 2) is achieved — NO extra probing needed.
    4. The bounds discipline: any decode of a response must length-check (report.type()==Long,
       report.feature()!=0, paramEnd-paramBegin >= N) before indexing — cite ACCESS-04 /
       BatteryStatus::decodeStatus as the pattern.

       e.g. GetState() -> (brightness, effect…); SetBrightness(value); SetEffect(id, params);
       plus capability props. Keep it small enough to satisfy LIGHT-01 fully, not a v1 subset.
    6. OPEN QUESTIONS / RISKS for Plan 02: anything unconfirmed (e.g. exact effect param encoding
