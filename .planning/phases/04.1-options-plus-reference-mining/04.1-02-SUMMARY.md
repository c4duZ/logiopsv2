# Phase 04.1 Plan 02: Options+ Smart-Action & App-Match Reference Specs Summary

Distilled two owned reference specs from the Options+ readable JSON data: a **smart-action/macro schema** (step + card vocabulary, for Phase 7) and an **app-match model** (application identity + the honest Windows-only detection report, for Phase 5). Both turn Logitech's readable `macros/`, `integrations/`, and `applications.json` into schemas WE own and cite, with nothing copied into `src/`.

## What Was Built

### Task 1 — `smart-action-schema.md` (commit `92585a9`)
The macro step model for Phase 7 (MACRO-01/02):
- **Step (`macro.type`) vocabulary table** from `predefined_win.json` with occurrence counts: `KEYSTROKE` (47), `TEXT_BLOCK` (53), `DELAY` (83), `INPUT_SEQUENCE` (73), `APP_WINDOWS_MANAGEMENT` (39), `OPEN_FILE_FOLDER` (10) — each with payload sub-object, fields, and our equivalent step.
- **Action enum**: `BRING_TO_FOREGROUND`/`MINIMIZE`/`MAXIMIZE`/`CLOSE` (full set from `common_application_cards_win.json`), plus the HID-usage note for keystroke codes.
- **Card model** (`id`, `name`, `attribute`=`MACRO_PLAYBACK`, `applicationId`, `continuous`, `tags`, `taskId`) + macro-preset lifecycle (`originType: PREDEFINED`, `state: ACTIVE`, `categories`: AI/FOR_DESIGNERS/FOR_DEVELOPERS/LEISURE/MEETINGS/PRODUCTIVITY) + card-map files.
- **Per-app integration cards**: `actionSdk.actions[]` shape (`name`/`actionId`/`actionIcon`/`parameters`) and the **8 bundled plugins** (photoshop, premiere_pro, illustrator, indesign, lightroom_classic, word, excel, powerpoint) with their target `application_id_*`.
- **Re-implementation note** tying to MACRO-01 (our ordered typed-step list) and MACRO-02 (session-helper privilege boundary).

### Task 2 — `app-match-model.md` (commit `14677e7`)
The app-match rule schema for Phase 5 (PROF-02/03):
- **Application entry schema** (22 apps): `applicationId`, `detection`, `cards`, `commands`, etc.
- **Honest match-rule report**: the `detection` block is **Windows-only** — `winRegistry` (`executable`+`registryPath`), `winExecutablePath` (templated `*.exe` path), `winStoreApp`. **No X11 `WM_CLASS`, no `bundleId`, no POSIX process field exists in the data.** Therefore PROF-03 (match by window class / executable) is explicitly flagged as OUR Linux rule layer, seeded by the Options+ `applicationId` taxonomy + Windows `*.exe` basenames as hints.
- **Card binding chain** `applicationId → detection → cards[] → macro`, including the first-class `MOUSE` step (`mouse.action`: `BUTTON`/`WIN_BACK`/`WIN_FORWARD`) present in `applications.json` but not in `predefined_win.json`.
- **Re-implementation note** for PROF-02 (default + per-app overrides via existing `ChangeProfile`) and PROF-03 (non-root session focus watcher matching `WM_CLASS`/executable).

## Key Decisions

1. **The Options+ data has no Linux match primitive.** `applications.json` detection is purely Windows (registry / `*.exe` basename / Store package). The spec is precise about this: the `applicationId` taxonomy is a usable *catalog*, but the actual focused-window match (`WM_CLASS` / resolved executable) is ours to design for Linux. This prevents Phase 5 from assuming a window-class field that does not exist.
2. **Unified step vocabulary across both data files.** `predefined_win.json` lacks a standalone `MOUSE` type (mouse appears via `hidUsage` inside `INPUT_SEQUENCE`); `applications.json` has first-class `MOUSE`/`ACTION`/`SYSTEM`. The smart-action spec accounts for the mouse/media step regardless.
3. **Privilege boundary recorded up front.** Process-spawn and window-management steps, and the focus watcher, are session-helper concerns — consistent with the standing root-daemon threat model.

## Deviations from Plan

None — plan executed exactly as written. (The plan anticipated the possibility that `applications.json` might not contain raw window-class/exe strings and asked to report honestly; the data in fact contains Windows-only executable/registry detection but no `WM_CLASS`, which is documented precisely per the plan's instruction.)
